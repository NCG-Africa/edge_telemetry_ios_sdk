## Part 1 — Overhead, ranked by host-app impact

| # | Site | What it costs | Trace v3 impact |
|---|------|---------------|-----------------|
| **O1** | `EdgeRumCore/Recorder.swift:532-543` → `Persistence/SessionSidecar.swift:85-102` | **Every recorded event synchronously JSON-encodes and atomically rewrites a file on the caller's thread.** `enqueue(_:)` calls `sidecar?.write(snapshot: context.snapshot())` outside the serial queue. `write` does `ensureDirectory` → `JSONEncoder.encode` → `Data.write(to:options:.atomic)`, and `.atomic` means write-temp + `rename(2)` — two syscalls plus an fsync-class barrier, per event. ## Part 2 — Plain bugs (not overhead)

| # | Site | Defect | Severity |
|---|------|--------|----------|
| **D1** | `EdgeRumCapture/HTTPCapture.swift:721` | **The internal session discards the host's session configuration entirely.** `URLSessionConfiguration.ephemeral` is built from scratch, so the host's `httpAdditionalHeaders`, `timeoutIntervalForRequest/Resource`, `allowsCellularAccess`, `waitsForConnectivity`, `httpCookieStorage`, `urlCredentialStorage`, `connectionProxyDictionary` and `httpMaximumConnectionsPerHost` are all silently replaced with Foundation defaults for **every instrumented request**. Cookies are the loudest: `.ephemeral` gets a private cookie store, so a cookie-session app's requests go out without its cookies. | **High** — behaviour change in the host app, caused by observation. |
| **D2** | `EdgeRumCapture/HTTPCapture.swift` (`EdgeRumMetricsDelegate`, `:794-840`) | The internal session's delegate implements **no authentication-challenge callback** (`urlSession(_:didReceive:completionHandler:)` is absent) and no `willPerformHTTPRedirection`. Challenges therefore fall to Foundation's default handling, and the host's own delegate — which is where cert pinning, mTLS client certs and custom trust evaluation live — **never sees them**. Any app that pins certificates in its `URLSessionDelegate` has its pinning bypassed for every instrumented request. | **High** — security-relevant. It weakens a host's TLS posture as a side effect of installing a RUM SDK. |
| **D3** | `EdgeRumCapture/HTTPCapture.swift:723-726` vs `:898-909` | **The recursion guard at `:724-726` is dead code, and the comment above it is wrong.** It reads `cfg.protocolClasses`, filters `EdgeRumURLProtocol` out, and assigns the result back. But only the **getter** is swizzled (`:889`) — the setter is not. When the internal `URLSession` later reads `protocolClasses` during load setup it calls the swizzled getter (`:898-909`), which unconditionally re-prepends `EdgeRumURLProtocol` (identifier is nil for `.ephemeral`, so the `:903` early-return does not fire, and the `:904` contains-check fails because the filter just removed it). The "belt + braces" is one brace: recursion is prevented **solely** by the `processedKey` request property (`:719` / `:692-694`). | **Medium** — not currently exploitable (the property guard holds), but it is a single point of failure documented as a double one, and T4 (#157) is about to add a second thing that must survive this same hop. |
| **D4** | `EdgeRumCapture/HTTPCapture.swift:205-221` vs `:768-776` | **Defense-in-depth check #2 is inert on the production path.** `shouldCaptureRequest` matches `taskDescription == "edge-rum-internal"`, which `BatchTransport` sets on *its own* task (`Transport/BatchTransport.swift:135`, `Transport/BackgroundUploader.swift:109`). But `recordOutcome` is passed `dataTask?.taskDescription` (`:776`) — the **internal** session's task, created at `:733`, which never inherits the host task's description. And `canInit(with:)` passes `taskDescription: nil` explicitly (`:702`), acknowledging the layer cannot see it. So of three "independent" checks, #2 never fires in either call site; the SDK's own uploads are filtered by the header (#1, `BatchTransport.swift:107`) and by `endpointHost` (#3) only — and #3 is a no-op when the host leaves `endpointHost` nil. | **Medium** — documented as three checks (`:12-16`, `CLAUDE.md`), is effectively one and a half. |
| **D5** | `EdgeRumCapture/HTTPCapture.swift:738-743` | `stopLoading()` cancels the task and invalidates the session **without calling `recordOutcome`**. Every cancelled request — user navigates away mid-load, `URLSession` cancels on timeout at the outer layer — is **silently dropped**: no `http.request` event at all. | **Medium**, and see T1 cross-ref: a root that minted for a cancelled request produces no child, which is indistinguishable from a coverage hole. |
| **D6** | `EdgeRumCapture/HTTPCapture.swift:732, 768-776` | `startedAt` is stamped in `startLoading()` (`:732`), which runs **on the URL loading system's queue**, not when the caller created or resumed the task. `http.duration_ms` (`:340`) therefore excludes the caller-side queueing delay. | **Medium** for this map specifically — the destination is *launch-to-request attribution*, and this is exactly the interval that goes missing. |
| **D7** | `EdgeRumCapture/HTTPCapture.swift:67-71` (doc) | The `HTTPCaptureConfig.sanitizeUrl` doc says "Applied on the caller thread before the URL becomes a wire value." **It is not.** The only production caller is `recordOutcome` from `didComplete` (`:768`), which runs on the internal session's delegate queue (`delegateQueue: nil` at `:730` → a Foundation-owned serial queue). The host's `sanitizeUrl` closure therefore runs on a background queue it was never told about, after the request has completed. Same for `ignoreUrls`. The ticket inherits this assumption — recording the correction here. | **Low** (docs/contract), but it invalidates a premise the ticket was written on. |
| **D8** | `EdgeRumCapture/HTTPCapture.swift:11-16` (doc) | Stale comment, already flagged in T1's resolution: the header describes a **class**-method swizzle on `URLSessionConfiguration.default`/`.ephemeral`. The code swizzles the **instance** getter for `protocolClasses` (`:844-888`), with a note at `:836-842` explaining that class-method swizzling SIGILLs on modern Foundation. | **Low** (docs). |
| **D9** | `EdgeRumCapture/HTTPCapture.swift:733` | `startLoading` always issues a `dataTask`, so a host's `downloadTask` is silently converted into an in-memory data load (see O5), and — **UNVERIFIED, needs a device** — `uploadTask(withStreamedRequest:)` bodies are at risk: `URLProtocol` is long known not to preserve `httpBodyStream` reliably, and `:715` copies only the `URLRequest`. If that reproduces, stream uploads are **corrupted**, not merely mis-measured. | **UNVERIFIED / potentially High.** Hand to T10 (#163), which already owns "what does the swizzled family actually reach". |

Fragility, not a live bug. | **Low.** |

## Part 3 — Per-request state, and what a `taskIdentifier`-keyed stash would join

The ticket asks what unbounded or unevicted per-request state already exists. **None.** All per-request state today lives on the `EdgeRumURLProtocol` *instance* — `dataTask`, `internalSession`, `receivedData`, `startedAt`, `finishedAt`, `collectedMetrics` (`:681-686`) — and is released when the URL loading system releases the protocol. There is no global dictionary keyed by anything.

That makes a `taskIdentifier`-keyed stash the **first** such structure, and three facts from this audit bound its design:

1. **`taskIdentifier` is unique per `URLSession`, not per process.** The outer task and the inner task at `:733` live in different sessions and will collide across sessions. A bare `taskIdentifier` key is wrong; a `(session, taskIdentifier)` pair or an associated object is the shape that survives.
2. **D5 is the eviction hazard.** `stopLoading()` returns without reaching `recordOutcome`, so a stash whose only removal point is the completion path leaks one entry per cancelled request, forever. Any stash needs an eviction trigger that fires on `stopLoading` too — or it needs to not be a stash at all.
3. **The object-lifetime alternative is already in the codebase and already correct.** `UIViewControllerCapture` uses `objc_setAssociatedObject` (`:292`) precisely so state dies with its owner, with the reasoning written out at `:175-178`. An associated object on the `URLSessionTask` inherits that property for free and sidesteps both hazards above.

This is evidence for **T4 (#157)**, which owns the marker mechanism. Not a decision here.

## Part 4 — Cross-references

- **T1 (#154)** — D3 and D4 sharpen the hop the marker must cross: the recursion guard is single-mechanism, and `taskDescription` does not survive to the inner task. D5 gives `injected_unattributed` a third cause (cancelled request, event never emitted) that T1's two-value scheme does not currently separate.
- **T2 (#155)** — O6's `mach_absolute_time()` site (`RunLoopObserverCapture.swift:167,170`) was **already adjudicated** by T2: sleep-exclusion is *correct* for a per-runloop-turn duration, and the suspected defect is refuted. The real clock defect T2 found is `HangWatchdog` deriving hang duration from `Date`, filed standalone as **#164**. O6 above is a separate, live finding about the *symbolication* on that path, not the clock.
- **T4 (#157)** — owns Part 3 entirely, plus D3.
- **T5 (#158)** — D6 is a direct input: the launch-to-first-request interval the map is named after is measured from `startLoading`, i.e. it silently omits the caller-side gap.
- **T10 (#163)** — owns D9 (download/upload coverage) and D1/D2 (which configurations and delegates the current design cannot honour, and whether a swizzle-based capture point changes that).
- **Map fog, patch 1 ("Offline replay vs root envelopes")** — now partly measured: `Transport/OfflineQueue.swift:69, 81, 89, 202-209` caps the queue at **200 batch files** (`EdgeRumConfig.maxQueueSize`, default 200) with **oldest-first FIFO eviction** (`trimToCapLocked`). Replay *delay* remains unbounded and unmeasured — drain is triggered by `enable()` and `didBecomeActive`, so a batch can replay arbitrarily later. The hazard stands; only the cap half of it is now quantified.

## What this audit did not do

No device run, no Instruments profile, no allocation counts. Every "costs X" above is a mechanism read off the source, and the two rows that most deserve a number — O1 (per-event atomic file write) and O3 (per-request session, no connection reuse) — are exactly the two where a measurement would change how loudly they should be argued. D9 cannot be settled without running it.
